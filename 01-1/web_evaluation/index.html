  • `css/style.css` (표현): 화면의 색상, 폰트, 여백, 다크모드, 반응형 레이아웃 등 외모를 전담합니다.
  • `js/*.js` (동작/로직): 클릭에 반응하고 데이터를 서버에서 받아와 화면을 바꾸는 신경망 역할을 전담합니다. 특히 JS 내부에서도 단일 책임 원칙(SRP)에 따라 통신(`api.js`), 렌더링(`ui.js`), 폼 검증(`events.js`), 전역 초기화(`main.js`)로 부품화하여 분리했습니다.

CSS 변수 관리 이점 답변

1) 일관성 유지: 브랜드 대표 색상(`--primary: #4f46e5`)을 한곳에 정의해 두면 수백 개의 버튼과 링크에서 같은 변수를 재사용하므로 색상이 어긋나지 않습니다.
2) 유지보수성 극대화: 메인 색상을 변경할 때 CSS 전체를 찾아바꿀 필요 없이 `:root`의 값 1줄만 수정하면 사이트 전체에 즉시 반영됩니다.
3) 런타임 다크모드 구현의 핵심: 자바스크립트로 수많은 요소의 인라인 스타일을 일일이 바꿀 필요 없이, 최상위 `[data-theme="dark"]`에서 변수 값만 바꿔주면 브라우저가 화면 전체 색상을 1프레임 만에 자동으로 다시 계산합니다. 

/* 라이트 모드 기본값 */
:root {
  --bg-primary: #f8fafc;
  --text-primary: #0f172a;
  --primary: #4f46e5;
}

/* 다크 모드 시 변수 값만 스왑 */
[data-theme="dark"] {
  --bg-primary: #0b0f19;
  --text-primary: #f8fafc;
  --primary: #6366f1;
}

3-2. `async/await`와 `try/catch`를 사용하여 API 호출 성공과 실패를 어떻게 분기 처리했는지 코드 흐름을 따라 답변할 수 있는가?

비동기 분기 제어 흐름

네트워크 통신은 언제든 실패할 수 있으므로, `try` 블록 안에서 `await fetch()`로 주문을 넣고 HTTP 응답 상태를 먼저 확인합니다.

  • HTTP 응답 분기: `response.ok`가 false이면 `403(Rate Limit)` 또는 `404(Not Found)` 에러를 강제로 `throw`하여 예외 처리로 보냅니다.
  • 성공 흐름: 정상일 때 `await response.json()`으로 데이터를 파싱하고, 저장소 개수에 따라 `SUCCESS` 상태 또는 `EMPTY` 상태를 반환합니다.
  • 실패 흐름: 인터넷 단절이나 에러 발생 시 즉시 `catch(error)` 블록이 실행되어, 프로그램 크래시 없이 `status: 'error'` 객체를 UI 함수에 넘겨 친절한 재시도 화면을 띄웁니다.
try {
  const res = await fetch(endpoint);
  if (!res.ok) {
    if (res.status === 403) throw new Error('API 한도 초과');
    throw new Error(`서버 오류: ${res.status}`);
  }
  const data = await res.json();
  return { status: 'success', data: data };
} catch (err) {
  return { status: 'error', error: err.message };
}

3-3. `map`, `filter` 등 배열 메서드를 활용하여 GitHub 데이터를 카드 UI로 변환하는 과정을 단계별로 정리할 수 있는가?

3단계 데이터 변환 파이프라인
  • 1단계 (`filter`): GitHub에서 받아온 전체 저장소 배열 중 내가 직접 만든 원본 저장소만 남기기 위해 `repos.filter(repo => !repo.fork)`로 포크된 저장소를 걸러냅니다.
  • 2단계 (`slice`): 화면 레이아웃 규격에 맞춰 상위 6개만 자릅니다 (`slice(0, 6)`).
  • 3단계 (`map`): 정제된 6개의 데이터 객체 배열을 순회하며, 각 객체를 HTML 카드 문자열로 1:1 변환합니다 (`repos.map(repo => \`<article class="project-card">...\</article>\`).join('')`).

4-1. 상태(STATE) 객체를 따로 만들어서 관리한 이유는 무엇이며, 그냥 변수로 처리하면 안 되는지 설명할 수 있는가?

상태 객체 관리의 필연적 이유

단순히 여기저기 전역 변수(`let theme = 'light'`, `let isLoading = false`, `let isError = false`)를 흩뿌려두면, 프로젝트 규모가 커질 때 "현재 화면이 어떤 상태인지" 추적할 수 없는 혼돈(State Spaghetti)이 발생합니다.

  • 불가능한 상태 방지: 변수를 각각 쓰면 실수로 `isLoading = true`인데 동시에 `isSuccess = true`가 되는 모순이 발생할 수 있습니다. 상태 객체(`API_STATUS = 'loading' | 'success' | 'error'`)로 관리하면 정확히 한 시점에 한 가지 상태만 가질 수 있도록 강제할 수 있습니다.
  • 단일 진실 공급원(Single Source of Truth): 모든 함수가 하나의 상태 객체만 바라보고 렌더링하므로, 버그가 생겼을 때 상태 객체 하나만 디버깅하면 즉시 원인을 찾을 수 있습니다. 이것이 React의 `useState`가 탄생한 근본적인 이유입니다.

4-2. 반응형 디자인에서 "모바일 퍼스트(Mobile-First)"로 작성한 이유를 이야기할 수 있는가?

모바일 퍼스트 선택 이유

1) 현대 웹 트래픽의 중심: 실제 웹 사용자 트래픽의 60% 이상이 스마트폰 모바일 환경에서 발생하므로 모바일을 기본 화면으로 설계하는 것이 자연스럽습니다.
2) 점진적 향상(Progressive Enhancement) 원칙: 좁은 모바일 화면을 먼저 설계하면 가장 핵심적인 콘텐츠에 집중하게 됩니다. 그 기본 구조 위에 `min-width: 768px`, `min-width: 1024px` 미디어 쿼리를 더해가며 더 넓은 화면에 맞는 레이아웃을 점진적으로 확장하는 방식이, 데스크톱용 무거운 스타일을 억지로 모바일용으로 덮어씌우는 것보다 CSS 코드가 훨씬 가볍고 오류가 적습니다.
