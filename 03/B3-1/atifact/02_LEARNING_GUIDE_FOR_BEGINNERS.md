# B3-1 초심자를 위한 AWS VPC & 웹 인프라 완전 정복 가이드 (LEARNING_GUIDE_FOR_BEGINNERS)

---

## 1. 개요 및 학습 목표

클라우드는 단순히 "원격에 있는 빠른 컴퓨터"를 대여하는 것이 아닙니다. 클라우드의 본질은 **소프트웨어로 정의된 격리된 데이터센터(Software-Defined Data Center)**를 구축하는 것입니다.
본 문서는 비전공자나 클라우드 입문자도 단 10분 만에 **VPC, Subnet, Internet Gateway, Route Table, Security Group, EC2, Nginx**의 유기적 동작 원리를 직관적으로 이해하고 스스로 설명할 수 있도록 일상적인 실생활 비유와 엄밀한 네트워크 기술 원리를 1:1로 매핑하여 설명합니다.

## 2. 실생활 비유로 단번에 이해하는 클라우드 인프라 모델링

복잡한 네트워크 용어들을 우리가 매일 마주하는 **"대단지 아파트와 택배 배송 시스템"**에 비유해 보겠습니다.

## 3. 핵심 구성 요소 3단계 해설 (비유 ➔ 기술 ➔ CLI)

### 1) VPC (Virtual Private Cloud)
- **1단계: 일상 비유**: 높은 콘크리트 담장으로 외부와 완전히 차단된 **"독립된 아파트 단지"**입니다. 담장이 없으면 아무나 단지 안을 돌아다닐 수 있어 위험합니다.
- **2단계: 기술 원리**: 논리적으로 완전히 격리된 가상 사설 네트워크(Software Defined Network)입니다. RFC 1918 사설 IP 대역(`10.0.0.0/16`)을 부여받아 최대 65,536개의 내부 사설 IP를 사용할 수 있습니다. 외부에서는 VPC 내부 사설 IP로 직접 접근할 수 없습니다.
- **3단계: CLI 파라미터**:
  ```bash
  aws ec2 create-vpc --cidr-block 10.0.0.0/16
  ```

### 2) 서브넷 (Subnet)
- **1단계: 일상 비유**: 아파트 단지 내부를 효율적으로 관리하기 위해 나눈 **"101동 구역, 102동 구역"**입니다.
- **2단계: 기술 원리**: VPC의 거대한 IP 블록을 작은 네트워크 단위로 쪼갠(Sub-network) 것입니다. 본 과제에서는 `10.0.1.0/24`(총 256개 주소 중 AWS 예약 5개를 제외한 251개 가용) 대역을 하나의 가용영역(`ap-northeast-2a`)에 할당합니다.
- **3단계: CLI 파라미터**:
  ```bash
  aws ec2 create-subnet --vpc-id <VPC_ID> --cidr-block 10.0.1.0/24 --availability-zone ap-northeast-2a
  ```

### 3) 인터넷 게이트웨이 (Internet Gateway, IGW)
- **1단계: 일상 비유**: 외부 공용 도로와 아파트 단지 내부 도로를 이어주는 **"단지 정문 톨게이트 및 안내소"**입니다.
- **2단계: 기술 원리**: VPC 내부 인스턴스가 공인 인터넷과 통신할 수 있도록 해주는 관문입니다. 수평 확장이 가능하고 가용성이 높은 소프트웨어 컴포넌트로, 사설 IP와 공인 IP 간의 **1:1 양방향 네트워크 주소 변환(1:1 NAT)**을 실시간으로 수행합니다.
- **3단계: CLI 파라미터**:
  ```bash
  aws ec2 create-internet-gateway
  aws ec2 attach-internet-gateway --vpc-id <VPC_ID> --internet-gateway-id <IGW_ID>
  ```

### 4) 라우팅 테이블 (Route Table)
- **1단계: 일상 비유**: 단지 교차로마다 세워진 **"교통 표지판 및 내비게이션"**입니다. "외부로 가려면 정문으로 가시오"라고 쓰여 있습니다.
- **2단계: 기술 원리**: 서브넷 내부에서 발생한 네트워크 패킷이 목적지 IP를 찾아갈 수 있도록 안내하는 규칙들의 모음입니다.
  - `10.0.0.0/16 -> local`: VPC 내부 통신은 내부에서 소화합니다.
  - `0.0.0.0/0 -> igw-xxxx`: 내부 사설 대역을 벗어난 모든 외부 목적지 트래픽은 IGW로 전송합니다.
- **3단계: CLI 파라미터**:
  ```bash
  aws ec2 create-route --route-table-id <RTB_ID> --destination-cidr-block 0.0.0.0/0 --gateway-id <IGW_ID>
  aws ec2 associate-route-table --subnet-id <SUBNET_ID> --route-table-id <RTB_ID>
  ```

### 5) 보안 그룹 (Security Group)
- **1단계: 일상 비유**: 아파트 각 동 1층에 설치된 **"공동현관 도어락 및 경비실"**입니다. 미리 등록된 손님만 문을 열어줍니다.
- **2단계: 기술 원리**: 가상 서버(EC2)의 네트워크 인터페이스(ENI)에 적용되는 **가상 방화벽(Stateful Firewall)**입니다.
  - **Stateful(상태 저장)**: 들어올 때 허용된 패킷(인바운드 80)은 나갈 때(아웃바운드) 별도 검사 없이 자동으로 통과됩니다.
  - **화이트리스트 기반**: 허용 규칙에 명시되지 않은 모든 인바운드 트래픽은 기본적으로 즉각 차단(Implicit Deny)됩니다.
- **3단계: CLI 파라미터**:
  ```bash
  aws ec2 authorize-security-group-ingress --group-id <SG_ID> --protocol tcp --port 80 --cidr 0.0.0.0/0
  aws ec2 authorize-security-group-ingress --group-id <SG_ID> --protocol tcp --port 22 --cidr <내공인IP>/32
  ```

### 6) EC2 (Elastic Compute Cloud) & Nginx
- **1단계: 일상 비유**: 101동 101호 입주 세대(EC2)와 그 안에서 손님의 방문을 친절하게 맞이하는 안내원(Nginx)입니다.
- **2단계: 기술 원리**: AWS 클라우드에서 제공하는 독립된 가상 머신(VM)이며, Nginx는 리눅스 OS 상에서 TCP 80번 포트를 항시 감시(Listen)하다가 HTTP 요청이 오면 200 OK 응답 본문을 돌려주는 고성능 비동기 웹 서버 소프트웨어입니다.
- **3단계: CLI 파라미터**:
  ```bash
  aws ec2 run-instances --image-id <AMI_ID> --instance-type t2.micro --key-name <KEY_NAME> --security-group-ids <SG_ID> --subnet-id <SUBNET_ID> --associate-public-ip-address
  ```

## 4. 패킷의 왕복 여행기 (Life of a Packet)

외부 사용자 브라우저가 `http://13.125.100.200/health`를 입력하고 엔터를 눌렀을 때 벌어지는 10단계의 여정입니다.

1. **[요청 시작]**: 사용자의 브라우저가 `TCP SYN` 패킷을 생성하여 목적지 공인 IP(`13.125.100.200:80`)로 전송합니다.
2. **[AWS 엣지 도달]**: 인터넷 백본망을 통과한 패킷이 AWS 서울 리전(`ap-northeast-2`)의 인터넷 게이트웨이(IGW)에 도달합니다.
3. **[1:1 NAT 변환]**: IGW는 공인 IP(`13.125.100.200`)를 내부 사설 IP(`10.0.1.50`)로 1:1 주소 변환(Destination NAT)합니다.
4. **[라우팅 조회]**: VPC 가상 라우터가 라우팅 테이블을 조회하여 해당 사설 IP가 속한 퍼블릭 서브넷(`10.0.1.0/24`)으로 패킷을 포워딩합니다.
5. **[보안 그룹 검사]**: EC2 앞단의 보안 그룹 엔진이 인바운드 룰을 검사합니다.
   - `TCP 80` 포트가 `0.0.0.0/0`에 허용되어 있으므로 패킷을 통과시킵니다.
   - 동시에 **Connection Tracking Table(연결 추적 테이블)**에 `[출발지: 사용자IP / 목적지: 10.0.1.50:80 / 상태: ESTABLISHED]`를 기록합니다.
6. **[OS 커널 수신]**: EC2의 Ubuntu Linux 커널 네트워크 스택이 패킷을 수신하고, 80번 포트를 바인딩하고 있는 소켓을 조회합니다.
7. **[Nginx 처리]**: Nginx 워커 프로세스가 시스템 콜(`accept`)로 요청을 수락하고 `GET /health` 요청에 대해 `HTTP/1.1 200 OK` 응답 헤더와 본문을 작성합니다.
8. **[응답 패킷 송신]**: Nginx가 `HTTP 200 OK` 응답 패킷을 사용자 IP를 목적지로 하여 송신합니다.
9. **[Stateful 아웃바운드 자동 통과]**: 응답 패킷이 보안 그룹에 도달했을 때, 연결 추적 테이블에 등록된 기존 세션이므로 **아웃바운드 규칙 검사 없이 즉각 통과**합니다.
10. **[IGW Source NAT 및 브라우저 렌더링]**: IGW가 출발지 사설 IP를 다시 공인 IP(`13.125.100.200`)로 변환하여 인터넷으로 쏘아 올리고, 사용자 브라우저 화면에 200 OK가 표시됩니다.

## 5. 학습자가 스스로 답할 수 있어야 하는 5대 핵심 질문 해설

### Q1. VPC, Subnet, Route Table, Internet Gateway가 각각 어떤 역할을 하며 트래픽 흐름이 어떻게 이어지는가?
> **모범 답변**:
> - **VPC**는 격리된 사설 가상 네트워크 경계를 제공하고, **Subnet**은 이를 가용영역별로 분할한 구역입니다.
> - **Internet Gateway(IGW)**는 외부 공인 인터넷과 VPC 내부 사설망 간의 주소 변환(1:1 NAT) 관문 역할을 합니다.
> - **Route Table**은 패킷의 이정표로서, `0.0.0.0/0`(외부 인터넷) 트래픽을 IGW로 보내도록 라우팅합니다.
> - 트래픽 흐름: `외부 클라이언트 ➔ IGW(공인 IP -> 사설 IP 변환) ➔ Route Table(서브넷 라우팅) ➔ Subnet ➔ Security Group(인바운드 80 허용) ➔ EC2(Nginx)` 순으로 이어집니다.

### Q2. Security Group과 IAM의 역할 차이는 무엇이며, 최소 권한 원칙은 왜/어떻게 적용하는가?
> **모범 답변**:
> - **차이점**: Security Group은 **네트워크 트래픽(IP 및 Port)**을 제어하는 방화벽이고, IAM은 **사람 또는 애플리케이션의 API 호출 행위(Identity & Access)**를 제어하는 권한 체계입니다.
> - **최소 권한 원칙의 이유**: 관리자 권한(`AdministratorAccess`)을 부여하면 자격증명 유출 시 공격자가 전체 계정을 장악하고 타 서비스(S3, RDS 등)를 파괴하거나 과금을 유발할 수 있습니다.
> - **적용 방법**: EC2 및 VPC의 생성/삭제/조회에 꼭 필요한 28개 Action(`ec2:CreateVpc`, `ec2:RunInstances` 등)만 명시된 커스텀 JSON 인라인 정책을 작성하여 사용자/역할에 연결합니다.

### Q3. 외부 요청이 EC2 웹 서버까지 도달하기 위해 필요한 3대 필수 설정은 무엇인가?
> **모범 답변**:
> 1. **인터넷 게이트웨이 및 라우팅 설정**: VPC에 IGW가 부착(Attach)되어 있고, 서브넷 라우팅 테이블에 `0.0.0.0/0 -> IGW` 규칙이 등록되어 있어야 합니다.
> 2. **퍼블릭 IP 할당**: EC2 인스턴스가 인터넷에서 식별 가능한 공인 IP(Public IPv4)를 보유하고 있어야 합니다.
> 3. **보안 그룹 인바운드 허용**: EC2에 연결된 보안 그룹의 인바운드 규칙에 HTTP `80` 포트가 `0.0.0.0/0` 소스로 개방되어 있어야 합니다. (어느 하나라도 누락되면 트래픽이 차단됩니다.)

### Q4. 오류 발생 시 로그/증상을 근거로 가설을 세우고, 검증 후 조치하는 트러블슈팅 절차는 무엇인가?
> **모범 답변**:
> 표준 6단계 프레임워크를 따릅니다:
> 1. **증상(Symptom)**: 브라우저 접속 시 무한 로딩(Connection Timeout) 발생.
> 2. **가설(Hypothesis)**: "서버가 죽었거나, 보안 그룹에서 80 포트가 닫혀 패킷이 드롭되고 있을 것이다."
> 3. **검증(Verification)**: EC2 콘솔 내부에서 `curl http://localhost` 실행 ➔ 200 OK 응답 확인(서버는 정상). 보안 그룹 인바운드 규칙 조회 ➔ 22 포트만 있고 80 포트가 누락됨을 실증.
> 4. **조치(Remediation)**: 보안 그룹에 `TCP 80, 0.0.0.0/0` 인바운드 룰을 추가.
> 5. **결과(Result)**: 외부 브라우저에서 즉시 HTTP 200 OK 응답 확인.
> 6. **재발방지(Prevention)**: IaC 스크립트에 보안 그룹 규칙 선언을 포함하여 수동 구성 실수를 영구 예방.

### Q5. 클라우드 과금이 발생하는 대표 요인은 무엇이며, 실습 리소스를 안전하게 정리하는 순서는 무엇인가?
> **모범 답변**:
> - **과금 요인**: 인스턴스를 '중지(Stop)' 상태로 방치해도 부착된 **EBS 볼륨의 프로비저닝 용량 비용**과 **미사용 탄력적 IP(EIP)의 유휴 페널티 비용**이 지속적으로 청구됩니다.
> - **안전한 정리 순서 (의존성 역순)**:
>   1. EC2 인스턴스 완전 **종료(Terminate)** (연결된 루트 EBS 자동 삭제 확인)
>   2. 탄력적 IP(EIP) 릴리스 (할당한 경우)
>   3. 보안 그룹(Security Group) 삭제
>   4. 라우팅 테이블 연결 해제 및 삭제
>   5. 인터넷 게이트웨이 Detach 및 삭제
>   6. 서브넷 및 VPC 최종 삭제 ➔ AWS Billing 대시보드 0원 확인.

## 6. 초심자가 가장 많이 겪는 오개념 격파 FAQ 8선

#### Q1. 인스턴스를 '중지(Stop)'해 두면 요금이 1원도 안 나오나요?
> **아닙니다! 절대 주의해야 합니다.**  
> 인스턴스를 중지하면 vCPU/RAM 연산 비용은 멈추지만, 하드디스크 역할을 하는 **EBS 볼륨 용량 비용(GB당 월 비용)**은 계속 청구됩니다. 또한 인스턴스에 고정 IP(EIP)가 붙어 있다면, 인스턴스가 꺼져 있는 동안 "IP 유휴 페널티 요금"이 시간당 부과됩니다. 실습이 끝나면 반드시 **종료(Terminate)**해야 합니다.

#### Q2. 보안 그룹에서 아웃바운드에 80 포트를 안 열었는데 어떻게 웹 페이지 응답이 브라우저로 돌아가나요?
> **보안 그룹이 'Stateful(상태 저장)' 방식이기 때문입니다.**  
> 인바운드로 허용된 요청이 들어오면, AWS 가상 방화벽이 해당 TCP 연결 세션을 내부 추적 테이블에 기억합니다. 따라서 그 연결에 대한 응답(Return Traffic)은 아웃바운드 규칙을 전혀 확인하지 않고 자동으로 통과시킵니다.

#### Q3. 보안 그룹(Security Group)과 네트워크 ACL(NACL)은 무엇이 다른가요?
> 보안 그룹은 **인스턴스(가상머신)** 단위로 동작하는 Stateful 방화벽(허용 규칙만 정의)이며, NACL은 **서브넷** 전체 단위로 동작하는 Stateless 방화벽(허용/차단 규칙 모두 정의 가능, 번호순 평가)입니다. 본 실습에서는 세밀한 호스트 제어가 가능한 보안 그룹을 기본 보안 계층으로 사용합니다.

#### Q4. SSH 포트(22)를 `0.0.0.0/0`으로 열어두면 왜 위험한가요?
> 전 세계 인터넷에는 취약한 서버를 찾아 무차별 대입 공격(Brute-force)과 봇 스캐닝을 수행하는 공격자들이 24시간 활동하고 있습니다. 22 포트가 전 세계에 열려 있으면 분당 수백 건의 무단 로그인 시도 공격을 받게 되며, 키페어가 유출되거나 취약점이 발생할 경우 서버가 즉각 장악됩니다. 따라서 반드시 관리자 본인의 공인 IP(`/32`)로 한정해야 합니다.

#### Q5. 서브넷 CIDR이 `10.0.1.0/24`이면 IP가 256개인데 왜 251개만 쓸 수 있나요?
> AWS는 모든 서브넷에서 **처음 4개 IP와 마지막 1개 IP(총 5개)**를 내부 인프라용으로 미리 예약하기 때문입니다.
> - `.0`: 네트워크 주소
> - `.1`: VPC 라우터 주소
> - `.2`: AWS DNS 서버 주소
> - `.3`: 미래 사용을 위해 AWS가 예약
> - `.255`: 네트워크 브로드캐스트 주소 (AWS VPC는 브로드캐스트를 지원하지 않으나 예약됨)

#### Q6. 퍼블릭 서브넷과 프라이빗 서브넷의 본질적인 기술적 차이는 무엇인가요?
> 서브넷 자체는 기술적으로 동일합니다. 차이는 **"연결된 라우팅 테이블에 `0.0.0.0/0 -> IGW` 규칙이 있는가 없는가"**뿐입니다. IGW로 향하는 기본 라우트가 있으면 **퍼블릭 서브넷**, 없으면 **프라이빗 서브넷**이 됩니다.

#### Q7. 왜 루트 계정(Root User)으로 과제를 진행하면 안 되나요?
> 루트 계정은 AWS 계정 내의 모든 리소스, 결제 정보, 계정 탈퇴 권한까지 가진 무소불위의 슈퍼 관리자입니다. 루트 계정의 액세스 키가 깃허브나 코드에 실수로 노출되면 수천만 원의 채굴 과금이 발생하거나 계정이 영구 삭제될 수 있습니다. 실무에서는 루트 계정에 MFA를 걸고 봉인한 뒤, 최소 권한만 부여된 IAM 계정을 사용하는 것이 철칙입니다.

#### Q8. Nginx 설치 후 `curl http://localhost`는 성공하는데 브라우저 접속이 안 될 때 가장 먼저 확인할 3가지는?
> 1. EC2 인스턴스에 **공인 IP(Public IPv4)**가 정상 할당되었는지 확인.
> 2. 보안 그룹 인바운드 규칙에 **TCP 80 포트(0.0.0.0/0)**가 등록되어 있는지 확인.
> 3. 서브넷의 라우팅 테이블에 **`0.0.0.0/0 -> IGW`** 라우팅이 결합되어 있는지 확인.
