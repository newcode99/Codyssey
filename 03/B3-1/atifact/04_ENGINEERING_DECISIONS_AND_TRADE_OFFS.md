# B3-1 엔지니어링 의사결정 및 기술 트레이드오프 분석서 (ENGINEERING_DECISIONS_AND_TRADE_OFFS)

---

## 1. 개요

인프라 엔지니어링에서 "정답"이란 존재하지 않으며, 주어진 비즈니스 요구사항과 비용, 보안, 운영 편의성 간의 **최적의 균형점(Trade-off)**을 찾아가는 과정이 있을 뿐입니다.
본 문서는 B3-1 AWS 인프라 설계 과정에서 내린 5대 핵심 엔지니어링 의사결정의 당위성과 비교 대안, 그리고 발생 가능한 엣지케이스에 대한 방어(Guard) 전략을 기술합니다.

---

## 2. 5대 핵심 엔지니어링 의사결정 및 Why

### [결정 1] Default VPC 대신 커스텀 VPC(`10.0.0.0/16`)를 직접 구축한 이유
- **배경**: AWS 계정 생성 시 리전마다 `172.31.0.0/16` 대역의 기본 VPC가 미리 생성되어 있어, 버튼 한 번으로 EC2를 띄울 수 있습니다.
- **Why**:
  1. **네트워크 격리 및 통제력 결여**: 기본 VPC는 모든 서브넷이 퍼블릭이며 기본 라우팅이 열려 있어 보안 거버넌스 측면에서 취약합니다.
  2. **IP 대역 충돌 방지**: 사내 온프레미스 망이나 타 클라우드 VPC와 Direct Connect 또는 VPN으로 피어링할 때 기본 VPC의 `172.31.0.0/16`은 흔히 대역 충돌(CIDR Overlap)을 일으킵니다.
  3. **인프라 원리 체득**: 서브넷 분할, 게이트웨이 바인딩, 라우팅 테이블 결합의 전체 생명주기를 직접 제어함으로써 클라우드 네트워크의 실질적 구조를 체득합니다.

### [결정 2] 보안 그룹(Security Group) 중심의 1차 방어선 구축 (SG vs NACL)
- **배경**: AWS VPC는 서브넷 레벨의 Network ACL과 인스턴스 레벨의 Security Group이라는 2단계 방화벽을 제공합니다.
- **트레이드오프 비교표**:

| 비교 항목 | 보안 그룹 (Security Group) | 네트워크 ACL (Network ACL) |
| :--- | :--- | :--- |
| **적용 단위** | 인스턴스 가상 네트워크 인터페이스(ENI) | 서브넷(Subnet) 경계 전체 |
| **동작 방식** | **Stateful (상태 저장)** | **Stateless (상태 비저장)** |
| **규칙 유형** | **허용(Allow) 규칙만 정의 가능** | **허용(Allow) 및 거부(Deny) 모두 가능** |
| **규칙 평가** | 모든 규칙을 종합하여 일치 항목 허용 | 규칙 번호(1~32766) 오름차순으로 순차 평가 |
| **반환 트래픽** | 인바운드 허용 시 아웃바운드 자동 통과 | 아웃바운드에 에페머럴 포트(1024~65535) 명시 필요 |
| **본 과제 채택** | **주력 방어선으로 채택** | 기본 규칙(모두 허용) 유지 |

- **Why**:
  웹 서버 인프라에서는 클라이언트의 동적 포트(에페머럴 포트)를 예측하기 어렵기 때문에, Stateless 방식인 NACL만 사용할 경우 아웃바운드에 불필요하게 넓은 포트 대역을 개방해야 하는 위험이 있습니다. Stateful한 보안 그룹을 채택함으로써 아웃바운드 홀을 최소화하고 직관적인 화이트리스트 접근 통제를 달성합니다.

### [결정 3] 탄력적 IP(EIP) 대신 '인스턴스 자동할당 퍼블릭 IP' 채택
- **배경**: EC2에 고정된 공인 IP를 부여하는 방법으로 탄력적 IP(Elastic IP)와 인스턴스 런치 시 자동 할당되는 퍼블릭 IP가 있습니다.
- **트레이드오프 비교표**:

| 항목 | 자동 할당 퍼블릭 IP (Auto-assign IP) | 탄력적 IP (Elastic IP, EIP) |
| :--- | :--- | :--- |
| **IP 고정성** | 인스턴스 중지 후 재시작 시 IP 변경됨 | 인스턴스를 재시작하거나 변경해도 영구 고정 |
| **비용 정책** | **완전 무료** | 인스턴스에 부착되어 실행 중일 때만 무료 |
| **과금 위험성** | **과금 위험 0%** (인스턴스 종료 시 즉시 소멸) | **인스턴스 중지/종료 시 유휴 페널티(시간당 과금) 발생** |
| **본 과제 채택** | **최우선 채택 (Zero-Billing 보장)** | 채택 제외 (과금 방지) |

- **Why**:
  본 과제의 절대 원칙 중 하나는 **"과금 0원 보장(Zero-Billing)"**입니다. 초심자가 EIP를 발급받고 인스턴스만 종료한 채 EIP 릴리스를 잊어버리면, AWS는 미사용 공인 IPv4 자원에 대해 시간당 요금을 계속 부과합니다. 따라서 인스턴스 라이프사이클과 완전히 연동되어 종료 시 자동 소멸되는 자동할당 퍼블릭 IP를 채택했습니다.

### [결정 4] 관리자 권한(`AdministratorAccess`) 배제 및 커스텀 JSON 인라인 정책 작성
- **배경**: 인프라 배포 시 권한 에러를 피하기 위해 많은 개발자가 편의상 `AdministratorAccess`를 부여합니다.
- **Why**:
  최소 권한 원칙(Principle of Least Privilege)은 단순한 권장 사항이 아니라 엔터프라이즈 클라우드 거버넌스의 절대 기준입니다. 스크립트 실행 권한을 EC2/VPC의 생성, 조회, 삭제에 필요한 28개 세부 Action으로 한정함으로써, 스크립트 토큰이 침해당하더라도 공격자가 타 서비스(S3, RDS, IAM 등)로 수평 이동(Lateral Movement)하거나 암호화폐 채굴 인스턴스를 생성하는 2차 피해를 원천 차단합니다.

### [결정 5] AWS 웹 콘솔 수동 클릭 대신 Bash CLI 스크립트(IaC) 채택
- **배경**: AWS 관리 콘솔은 마우스 클릭으로 시각적 구성이 가능하지만, 스크립트는 사전 작성이 필요합니다.
- **Why**:
  1. **인적 오류(Human Error) 배제**: 콘솔 작업 시 "퍼블릭 IP 자동 할당" 체크박스 누락, 라우팅 테이블 연결 누락 등의 실수가 빈번합니다.
  2. **재현성(Reproducibility)과 멱등성**: 스크립트는 언제 어디서나 동일한 인프라를 수 초 만에 오차 없이 생성하고, 종료 시 잔존 자원 없이 100% 완전 파기할 수 있습니다.
  3. **코드형 인프라(Infrastructure as Code)의 기초**: 향후 Terraform, CloudFormation으로 확장하기 위한 엔지니어링 기초 체력을 다집니다.

## 3. 시스템 붕괴를 방어하는 4대 Guard 전략 (Failure Modes & Defenses)

```
[인프라 위험 요인]                      [Guard 방어 아키텍처]
┌───────────────────────────┐          ┌───────────────────────────────────────────┐
│ 1. IP 대역 고갈 위험       │ ───────> │ VPC /16 및 서브넷 /24로 251개 충분한 IP 확보│
├───────────────────────────┤          ├───────────────────────────────────────────┤
│ 2. 비대칭 라우팅 루프     │ ───────> │ 서브넷 단위 명시적 Route Table 1:1 결합   │
├───────────────────────────┤          ├───────────────────────────────────────────┤
│ 3. SSH 브루트포스 공격     │ ───────> │ 22번 포트를 관리자 공인 IP/32로 강력 제한 │
├───────────────────────────┤          ├───────────────────────────────────────────┤
│ 4. 유휴 리소스 과금 폭탄   │ ───────> │ DeleteOnTermination: true + 철거 스크립트 │
└───────────────────────────┘          └───────────────────────────────────────────┘
```

### [Guard-1] 서브넷 IP 고갈 및 확장성 방어
- **위험**: 서브넷을 `/28`(가용 IP 11개) 등으로 너무 좁게 설정하면 오토스케일링이나 컨테이너 증설 시 즉시 IP 고갈로 장애가 발생합니다.
- **방어**: 본 과제는 `10.0.1.0/24`를 채택하여 251개의 가용 호스트를 확보하고, VPC 대역(`10.0.0.0/16`) 내에 향후 프라이빗 서브넷(`10.0.2.0/24`, `10.0.3.0/24`)을 최대 250개 이상 증설할 수 있는 확장 여유를 보장했습니다.

### [Guard-2] 비대칭 라우팅 및 패킷 블랙홀 방어
- **위험**: 메인 라우팅 테이블을 임의로 수정하다가 내부 트래픽이 외부로 빠져나가거나 패킷이 라우팅 루프에 빠져 유실(Blackhole)되는 현상.
- **방어**: VPC 기본(Default) 라우팅 테이블을 건드리지 않고, 전용 **커스텀 라우팅 테이블(`rtb-custom`)**을 신규 생성하여 퍼블릭 서브넷과 명시적으로 연결(Explicit Subnet Association)했습니다.

### [Guard-3] SSH 무차별 대입 공격(Brute-force) 방어
- **위험**: 22번 포트를 `0.0.0.0/0`으로 개방하면 분당 수백 건의 무단 SSH 로그인 시도가 발생하여 CPU 자원을 잠식하고 계정 탈취 위험에 노출됩니다.
- **방어**: `curl -s https://checkip.amazonaws.com` 명령어로 배포자의 실제 공인 IP를 동적으로 추출하여, 오직 해당 IP(`x.x.x.x/32`)에 대해서만 22번 포트 인바운드를 허용하는 방어 규칙을 적용했습니다.

### [Guard-4] EBS 유휴 볼륨 누적 과금 방어
- **위험**: EC2 인스턴스를 종료(Terminate)하더라도 루트 볼륨 외에 추가 볼륨이 남아있거나, 종료 옵션이 잘못되어 볼륨이 'Available' 상태로 남아 매달 GB당 과금이 발생하는 현상.
- **방어**: 인스턴스 프로비저닝 시 `BlockDeviceMappings` 설정에서 `DeleteOnTermination: true` 속성을 명시적으로 강제하고, `cleanup_infra.sh`에서 볼륨 잔존 여부를 2차로 전수 스캔하여 완전 파기하도록 구현했습니다.
